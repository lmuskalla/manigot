TASK-12: session.log SSE streaming endpoint. GET /projects/{project}/jobs/{job}/session-log/stream — Server-Sent Events, chosen over WebSocket per the brief's own steer ("pick whichever is less code against the existing net/http server"): SSE is plain HTTP response streaming with no upgrade handshake or framing and needs no new dependency, unlike WebSocket, which Go's stdlib doesn't support natively. Implementation: open the job's session.log, seek to EOF (or accept a ?from=<byte offset> query param mirroring readFileTail's tail semantics for a client reconnecting after a drop), then poll for growth on a short interval (e.g. 500ms — the file is a local append-only file, so a simple stat+read-new-bytes loop is sufficient; no fsnotify/inotify needed) and flush each new chunk as an SSE `data:` frame (http.Flusher). Must stop cleanly on client disconnect (r.Context().Done()) AND participate in the daemon's graceful shutdown drain (serveShutdownDrain in cmd/mg/serve.go): plain http.Server.Shutdown does NOT itself interrupt a handler stuck in a polling loop — it only stops accepting new connections and waits for in-flight handlers to return — so the Server struct needs its own shutdown signal (e.g. a context stored on *Server, cancelled at the top of Shutdown before calling s.http.Shutdown) that this handler selects on alongside the request context and its poll ticker. Without this, every open stream would force the daemon to wait out the full drain timeout on every graceful shutdown — exactly what the brief calls out to confirm/avoid.
     files: src/internal/serve/server.go (Server gets a shutdown context/field), src/internal/serve/stream.go (new), src/internal/serve/stream_test.go (new — httptest-driven: asserts growth is observed live, disconnect stops the handler goroutine, and a simulated shutdown returns promptly rather than hanging)
     depends: none structurally, but a realistic end-to-end test benefits from TASK-1/TASK-2 already writing something to session.log during a launch
     risk: high — the graceful-shutdown interaction is the one correctness requirement the brief explicitly calls out as needing verification, and a background-goroutine-per-stream shape is new to this codebase; getting it wrong leaks goroutines or hangs shutdown.
